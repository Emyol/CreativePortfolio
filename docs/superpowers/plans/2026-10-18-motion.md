# Motion, entrance and real 3D player: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the motion system in the spec:

- a screen-first entrance;
- sections that hold until their own arrival has played, each with a toy;
- a real-time 3D player for the hero, the flip and the footer;
- an event page that writes itself in after the existing photo morph.

**Architecture:**

- **Holds.** A pure hold rule (`lib/motion/hold.ts`) and one hook (`useHold`) pin a section and
  scrub an `Arrival` (from a per-track registry) over the visitor's scroll.
- **Toys.** Small client wrappers (`Throwable`, `Tilt`, `CueRow`, `Spine`) add the toys to the
  existing server-rendered section components, without changing their content or semantics.
- **3D.** One lazily imported three.js stage (`lib/three/stage.ts`) owns a single fixed
  canvas. It renders a "view" per DOM placeholder (hero, flip, footer) with scissoring. Each
  view clones one compressed GLB exported from the existing Blender script.
- **Fallback.** The sprite device stays as the poster and the fallback.

**Tech Stack:** Next.js 16.4, React 19.3, TypeScript, CSS Modules, GSAP 3.15 (ScrollTrigger,
Draggable, InertiaPlugin, already installed), Lenis, three.js (new), glTF-Transform (new, dev),
Blender 5.2 headless, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-18-motion-design.md`. The mockups with exact timings
are in `docs/superpowers/mockups/2026-10-18-motion/`: `entrance.html`, `sections.html`,
`hero-3d.html`, `spike-export-glb.py`, `spike-turnover.py`. Read them as the reference for
feel. Don't port them line by line.

## Global Constraints

**Git and process**

- Branch `feat/motion` from `docs/motion-spec`, so the spec and mockups travel with it.
- Conventional commits explaining *why*.
- **No Claude attribution**: no `Co-Authored-By`, no "Generated with".
- Never stage `.env*`, `.impeccable/`, `.arena/` or scratch.
- Before writing Next code, read the relevant guide in `node_modules/next/dist/docs/`.
- Run `pick-ui-library` before adding a dependency (three, glTF-Transform).

**Content and accessibility**

- **Never invent content. No phone number anywhere.** Motion never adds content. The mixtape
  bars are decorative.
- Text is in the DOM at all times. Reveals use clip-path, opacity and transforms, never
  `textContent` slicing.
- Keyboard paths where they carry meaning.
- 44 px minimum targets.
- Visible focus.
- Every GSAP setup lives in `useGSAP` or `gsap.context` and reverts on unmount. Every three.js
  object and listener is disposed on unmount.

**Motion tiers** (`lib/motion/tier.ts`):

- **`full`** (desktop): everything.
- **`lite`** (phones):
  - holds at **60%** of the desktop distance;
  - the 3D hero at a pixel ratio of at most **1.5**, with no cursor tilt (a gentle idle sway)
    and no drag-turn;
  - drag toys become taps;
  - no event tilt.
- **`none`** (reduced motion, live):
  - no entrance, holds or scrubbing;
  - **no `<canvas>`**: the sprite device, still;
  - content complete;
  - interactions work without animation.

**Holds**

- **Distances at desktop:** about 650 (about), 900 (events), 800 (mixtape), 1100 (people),
  850 (made), 700 (on rotation), 1000 (footer) px.
- **Scrub:** `scrub: true`.
- **Rest:** a still rest of **15%** of the timeline at the end.
- **Pin:** the section, never an element that is itself animated.

**Entrance timings:** as the spec's table. It skips on any input, never waits for the network,
and plays once per session (`POWER_KEY`). It never plays under reduced motion, at a deep link,
or when coming back.

**3D budget:**

- Added JS at most about **200 KB gz**. The GLB at most about **500 KB**.
- Loaded after first paint. LCP stays the sprite plate.
- Device pixel ratio at most 2.
- Render only views on screen; pause in hidden tabs.

**Frame rate:** the automated test browser presents WebGL at about 1 fps on the dev machine.
Never assert frame rate in e2e. Check smoothness in a real browser and report it to the owner.

## Review Focus

These are the failure modes the spec implies but no feature test exercises directly. Each has
a test in its owning task.

1. **A dock key or deep link that jumps across several holds** must land on the target settled
   (`data-arrival="1.00"`), with its heading at the top. Task 1, `e2e/holds.spec.ts`:
   "a dock key jumps across holds and lands settled".
2. **A resize while a section is held** keeps it fully in view; the start rule is recomputed.
   Task 1: "resizing mid-hold keeps the section in view".
3. **A section taller than the screen** (a short viewport) holds with its top in view, and its
   later rows arrive as they enter. Task 3, events at 1440×600: "a tall section holds its top
   and reveals later rows on entry".
4. **WebGL unavailable or lost.** The sprite device shows, the entrance still plays on it, and
   there are no console errors. Task 12, `e2e/hero3d.spec.ts`: "without WebGL the sprite
   device and the entrance still work".
5. **Home → event page → back.** Exactly one canvas, no replayed entrance, holds rebuilt and
   working. Task 15: "going to an event and back leaves one canvas and working holds".
